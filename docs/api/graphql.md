# WaterLens application API — GraphQL guide

The decision record is ADR 0003. The schema is `packages/contracts/schema.graphql`,
generated by `npm run contracts`. The endpoint is `POST /graphql`.

HTTP stays for:

- health: `/healthz`, `/readyz`;
- authenticated event streams: `/v1/jobs/{id}/events`, `/v1/agent-runs/{id}/events`;
- authorized downloads: `/v1/proposals/{id}/download`.

The HTTP routes are described in `packages/contracts/openapi.json`.

## Identity and authorization

- Every request may carry `Authorization: Bearer <Firebase ID token>`. The server
  verifies it and derives `uid` and the account kind (`GUEST` or `PERMANENT`) from it.
  **No input accepts a user or owner id**, and `ownerUid` is rejected by the schema
  itself. Guests are anonymous Firebase accounts (`sign_in_provider: anonymous`), never
  an unauthenticated hash.
- Verification (ADR 0004):
  - **Pilot:** Firebase Admin SDK `verify_id_token(check_revoked=True)` with Application
    Default Credentials. The verifier refuses to start for a `demo-*` project or when
    `FIREBASE_AUTH_EMULATOR_HOST` is set, because the SDK then accepts unsigned tokens.
  - **Local:** unsigned emulator tokens for `demo-waterlens` only, each checked against
    the emulator's account record, so deleted, disabled and revoked accounts are rejected.
- An invalid, expired or revoked token is treated as no token, so identity-requiring
  operations answer `UNAUTHENTICATED`. If the verifier itself is unreachable the request
  fails with HTTP 503 instead, so an outage never looks like a sign-out.
- The web client retries a request once with a force-refreshed token after
  `UNAUTHENTICATED`. That is safe for mutations: the operation did not run.
- Queries otherwise retry (up to 3 times) only after transport failures, `INTERNAL` or
  `SERVICE_UNAVAILABLE`. A definitive answer such as `NOT_FOUND`, `FORBIDDEN` or
  `VALIDATION_FAILED` is shown at once (`shouldRetryQuery` in `graphql/queryClient.ts`).
- Every resolver goes through an application service that checks ownership or
  membership. A private record you may not see returns `NOT_FOUND`, so its existence is
  not revealed. `FORBIDDEN` means you can see the record but lack the role for that
  action.
- Guests can create and edit their planning session.
- These actions need a permanent account: finalizing reports, generating proposals,
  creating or joining communities, and starting or recording tracking.
- Provisional policy, pending ADR 0002's open questions: community reports are finalized
  by coordinators, and only coordinators archive communities.

| Record                 | Who can read                           | Who can change                           |
| ---------------------- | -------------------------------------- | ---------------------------------------- |
| Area, coverage         | Anyone                                 | Catalogue only                           |
| Planning session       | Owner                                  | Owner (`expectedVersion`)                |
| Plan options, matches  | Session owner                          | `matchFunding` (session owner)           |
| Report                 | Owner; active members of its community | Archive: owner or community coordinator  |
| Proposal               | Readers of its report                  | Generate: owner or community coordinator |
| Community              | Anyone (members list: members only)    | Archive: coordinators. Join/leave: self  |
| Implementation project | Owner; active members of its community | Milestones: owner. Observations: readers |
| Job, agent run         | Owner                                  | System only                              |

## Mutation conventions

- Each mutation takes a single `input` and returns `XPayload { <result>, error }`.
- `error` is a `MutationError`:

  ```graphql
  type MutationError {
    code: ErrorCode!
    message: String!
    fieldErrors: [FieldError!]!
    currentVersion: Int
    requestId: String!
  }
  ```

- **Creates** carry `idempotencyKey: String!`: 16–128 characters of `A–Z a–z 0–9 _ -`,
  scoped to the verified user and the mutation. Repeating the same key with the same
  input returns the original result. Reusing it with different input returns
  `IDEMPOTENCY_KEY_REUSED`. Generate one key per user intent and reuse it when retrying
  that intent.
- **Updates** carry `expectedVersion: Int!`. A mismatch returns `VERSION_CONFLICT` with
  `currentVersion`; refetch, then reapply or ask the user. Every successful write
  increments `version`.
- **Patches**: for `updatePlanningSession.patch`, omitted fields are unchanged and `null`
  clears a field. Changing `areaId` clears the scenario and the selected plan.

| Mutation                     | Safety input      | Notes                                                                                                  |
| ---------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------ |
| `createPlanningSession`      | `idempotencyKey`  | Closes the caller's previous active session (no drafts)                                                |
| `updatePlanningSession`      | `expectedVersion` | Mode, stage, area, goal, scenario, selected plan                                                       |
| `matchFunding`               | `idempotencyKey`  | Deterministic per-criterion results; no percentage                                                     |
| `finalizeReport`             | `idempotencyKey`  | Permanent account; needs area, goal and selected plan                                                  |
| `archiveReport`              | `expectedVersion` | Archived reports are read-only (`ARCHIVED`)                                                            |
| `generateProposal`           | `idempotencyKey`  | Creates a proposal and a durable job (`QUEUED`)                                                        |
| `createCommunity`            | `idempotencyKey`  | Creator becomes coordinator                                                                            |
| `joinCommunity`              | `idempotencyKey`  | Immediate; archived communities return `ARCHIVED`                                                      |
| `leaveCommunity`             | `expectedVersion` | The caller's membership version; the last coordinator cannot leave                                     |
| `archiveCommunity`           | `expectedVersion` | Coordinators only                                                                                      |
| `startImplementationProject` | `idempotencyKey`  | From a finalized report; optional milestones                                                           |
| `updateMilestone`            | `expectedVersion` | Project owner                                                                                          |
| `recordObservation`          | `idempotencyKey`  | Explicit canonical unit; evidence starts `RECORDED`                                                    |
| `recordManualInput`          | `idempotencyKey`  | Caller's own session with a saved area; exact unit conversion; shown as `USER_ENTERED`, never measured |
| `beginAccountClaim`          | none (one-time)   | Guest only; returns the claim and its secret once                                                      |
| `completeAccountClaim`       | `idempotencyKey`  | Permanent account signed in within 5 minutes, plus the secret                                          |
| `cancelAccountClaim`         | `expectedVersion` | Guest that opened the claim                                                                            |

## Planning session inputs

`PlanningSession.inputsRevision` (and `PlanOption.inputsRevision`) count real changes to
the inputs that derived results depend on: `areaId`, `goal` and `scenario`, plus every
value recorded with `recordManualInput` for the session (it changes the baseline). Mode,
stage and an unchanged value never bump it. In the same transaction, the server applies
the dependency rules: a new area clears the scenario and the selected plan; a new goal, a
new scenario or a recorded value clears the selected plan (ADR 0012). Previewing a
scenario changes nothing. After `recordManualInput` the web client refreshes the session,
because its version moved.
`selectedPlanOptionId` must name an option computed for the session's resulting
revision, otherwise the update fails with `PRECONDITION_FAILED` and the field error
`selectedPlanOptionId`, so a plan can never be chosen for inputs it was not compared on.
`planOptions(sessionId)` lists only options computed for the session's current
`inputsRevision`, so after any input edit the list is empty until plans are compared
again (ADR 0011). A goal in an update is validated by the same rules as `checkGoal`
below; an invalid goal fails with `VALIDATION_FAILED` and `goal.…` field errors.
A closed session (replaced by `createPlanningSession`) answers `PRECONDITION_FAILED`
without a field error.

The web client keeps one coordinator per identity (`apps/web/src/session/`, ADR 0006):
structured patches on top of the last acknowledged version, `expectedVersion` on every
write, merge-on-conflict, and a small IndexedDB recovery record. Both planning modes use
it, so they share one session id and the same query keys.

## Account claims

Linking a new Google or email credential to a guest keeps the guest's uid, so nothing has
to move. A claim is only for the conflict case: the credential already belongs to an
existing account (`auth/credential-already-in-use`, or the user signs in to an existing
email account). The client then:

1. calls `beginAccountClaim` **while still signed in as the guest**. The server stores
   only a SHA-256 of the returned `claimSecret`; the claim expires after 10 minutes (server setting
   `WL_ACCOUNT_CLAIM_TTL_SECONDS`) and a new claim cancels the guest's previous open one;
2. signs in to the existing account (fresh sign-in);
3. calls `completeAccountClaim` with the secret and an idempotency key, retrying with the
   same key on network failure. If sign-in fails or is cancelled, it calls
   `cancelAccountClaim` instead.

Completion needs control of both identities: the guest proved it by opening the claim,
and the account proves it with a token whose `auth_time` is under 5 minutes old
(`WL_ACCOUNT_CLAIM_FRESH_SIGN_IN_SECONDS`; `REAUTHENTICATION_REQUIRED` otherwise). The guest uid comes only from the claim record,
never from client input.

The transfer is deliberately narrow:

- moved: the guest's **active planning session** and the funding matches computed for it;
- closed: the account's previously active session (one active session per user);
- not moved: closed sessions, jobs, agent runs and the anonymous Firebase user. Accounts
  are never merged.

A completed, cancelled or expired claim cannot be used again (`PRECONDITION_FAILED`);
completing your own claim again with the same key returns the original result. An unknown
claim or a wrong secret returns `NOT_FOUND`.

## Error codes

| Code                         | HTTP equivalent | Meaning / client action                                             |
| ---------------------------- | --------------- | ------------------------------------------------------------------- |
| `UNAUTHENTICATED`            | 401             | Missing, expired or invalid token. Sign in or refresh.              |
| `REAUTHENTICATION_REQUIRED`  | 401             | Sign-in too old for this action (claims). Sign in again.            |
| `PERMANENT_ACCOUNT_REQUIRED` | 403             | Guest attempting a permanent-only action. Offer account linking.    |
| `FORBIDDEN`                  | 403             | Visible record, missing role. Say who can do it.                    |
| `NOT_FOUND`                  | 404             | Missing, or not visible to you.                                     |
| `VALIDATION_FAILED`          | 422             | See `fieldErrors` (camelCase paths, e.g. `goal.budget.minorUnits`). |
| `VERSION_CONFLICT`           | 409             | Stale `expectedVersion`. Refetch.                                   |
| `IDEMPOTENCY_KEY_REUSED`     | 409             | Key reused with different input. Use a new key for a new intent.    |
| `PRECONDITION_FAILED`        | 409             | Missing prerequisite (e.g. no selected plan). Message says which.   |
| `ARCHIVED`                   | 409             | Record is read-only.                                                |
| `UNSUPPORTED_CURRENCY`       | 422             | Currency not in the reviewed list.                                  |
| `CURRENCY_MISMATCH`          | 422             | Cross-currency arithmetic attempted.                                |
| `BUDGET_EXHAUSTED`           | 429             | Usage budget reached (AI features; later phases).                   |
| `SERVICE_UNAVAILABLE`        | 503             | Data store or token verifier unreachable. Retry later.              |
| `INTERNAL`                   | 500             | Unexpected error, masked. Quote `requestId`.                        |

Queries put the code in `errors[].extensions.code`, with `requestId` beside it.
Query-validation, depth and token-limit errors use `VALIDATION_FAILED`.

## Data readiness

`Area.readiness(sessionId)` returns per-capability, per-input and per-metric states
(`AVAILABLE`, `USER_ENTERED`, `PARTIAL`, `STALE`, `UNAVAILABLE`), each with plain reasons.
Inputs also carry the action that would unblock them and whether manual entry is allowed.
Without `sessionId` it is public and uses only imported sources. With one, the caller
must own the session and the session's saved area must be this area; that session's
entered values are included. Results fed by synthetic demo data have `demo: true`, and
that data is used only in local mode. `Area.coverage` derives from the same assessment.
It carries no metric values; those come from `Area.baseline` (below), and only where
readiness allows. See ADR 0008 and `docs/data-readiness.md`.

## Baseline

`Area.baseline(sessionId)` returns the area's water baseline, calculated by the
deterministic engine in `domain/baseline.py` (ADR 0010). It uses the same access rules as
readiness. Without `sessionId` it is public and uses imported sources only. With one, the
caller must own the session, otherwise the result is `NOT_FOUND`, or `UNAUTHENTICATED`
when the caller is signed out. That session's entered values are then included.

- `Baseline`:
  - `id` (`bsl_…`, stable for the same evidence, and new when an input or source
    version changes), `asOf`, `engineVersion`, `exceedanceP`;
  - `window` (`start`, `endExclusive`, `days`) and `windowDays`;
  - `demo` and `basis` (`SOURCED`, `LIMITED` or `USER_INPUT`);
  - `metrics`, `indicators` and `chart`;
  - `missingEssentials`, `missingOptional` and `notes`.
- `BaselineMetric`:
  - `metric`, `name`, `formula`, `unit`, `daily` (whether the metric is defined day by
    day);
  - `availability`: `AVAILABLE`, `PROVISIONAL` (for example, it uses entered values or
    covers only part of the window), or `UNAVAILABLE`;
  - when there is a value: `exact` (an integer or `p/q`) and `value` (a decimal string);
  - when unavailable: `reason` (a `BaselineReason`). Either way, `reasons` gives the
    plain-language explanations;
  - `origin` (`MEASURED`, `USER_ESTIMATE` or `MODELED`), `asOf`, `demo`;
  - `recordedDays` and `periodDays` when the value comes from records. A value that
    averages fewer recorded days than the period is never `AVAILABLE` (the server
    refuses to build one), and the card says "Average of N of M days";
  - `assumptions`, `supporting` (for example `daily_deficit_total` in L), and `evidence`.
    Each `EvidenceLink` has the input or capability, snapshot or manual input id, title,
    publisher, URL, as-of, quality, method, uncertainty, note and `demo`.

  A missing value is always `null` with a reason, never `"0"`.

- `BaselineIndicator`:
  - context indicators: rainfall, groundwater, surface water, water quality, flood risk
    and land cover;
  - each has `statistic`, `unit`, `availability`, `observedOn` or `window`, `origin` and
    `evidence`;
  - an indicator has a value only when its capability is ready and its unit is
    compatible;
  - category indicators return `UNSUPPORTED_FORMAT`.
- `BaselineChart`:
  - `monthly`;
  - `buckets` (`DateWindow`s);
  - `series` (`key`; `values` as exact decimal strings in L/day, with `null` for a
    bucket that has any missing day; `origin` and `demo`, using the same rule as the
    cards).

Rates are canonical L/day. The web converts them for display only, using exact string
arithmetic and one unit per baseline:

- MLD, or kL/day when every nonzero rate is below 1 MLD;
- for US customary areas, MGD, meaning million US gallons per day (1 US gallon =
  3.785411784 L exactly).

## Goals and constraints

ADR 0011. The goal is part of the planning session (`PlanningSession.goal`), saved
through `updatePlanningSession` with `expectedVersion`. A changed goal bumps
`inputsRevision` and clears the selected plan.

- `GoalInput` / `Goal`:
  - `kind` (`REDUCE_SHORTAGE`, `IMPROVE_GROUNDWATER`, `REDUCE_WATER_BILLS`,
    `REDUCE_FLOOD_RISK`, `IMPROVE_WATER_QUALITY`, `REDUCE_TANKER_DEPENDENCE`, `CUSTOM`),
    `description`, and `confirmed` (custom wording must be confirmed);
  - `target` (`mode`: `RELATIVE_REDUCTION` with a `RATIO` quantity such as `"0.3"`, or
    `ABSOLUTE_LEVEL` with a unit allowed for the kind), and `targetParameter` for water
    quality;
  - `budget` (`minorUnits`, `currency`), `timelineDays` (maximum implementation time),
    `horizonDays` (planning horizon) and `priority`;
  - `also`: up to three further standard objectives;
  - `site`: `scale`, `roofArea` and `openGround` (`SQUARE_METRE`), `storageSpace`,
    `pipedSupply` and `restrictions` (`NO_EXCAVATION`, `NO_STRUCTURAL_CHANGES`,
    `NO_RECHARGE`, `NO_GREYWATER_REUSE`, `NO_PERMIT_WORKS`);
  - `preferredInterventions`: a measure whose site prerequisites are unmet, or that a
    restriction blocks, is a field error;
  - `estimates`: the user's own cost range and/or build days per measure, in the goal's
    currency, with a note, plus `effects` (`key`, `low`, `high`): ranges for the
    measure's catalogue `effectInputs`, in their canonical units (shares as ratios),
    checked against the catalogue's keys and bounds.

  Values are canonical. Formatted strings (`"10,00,000"`, `"30%"`) are rejected, never
  parsed.

- `Query.checkGoal(sessionId, goal)` returns `GoalCheck { errors, assessment }` without
  saving. `errors` are field errors (`goal.target.quantity.value`, …). `assessment` is
  `null` when there are errors.
- `PlanningSession.goalAssessment` gives the same assessment for the saved goal.
- `GoalAssessment`:
  - `outcome` (`FEASIBLE`, `INFEASIBLE`, `NOT_ASSESSABLE`), `summary` and `nextSteps`;
  - `target` (the outcome, message, metric, unit, baseline value and target level as
    exact decimal strings, and caveats);
  - `constraints` and `conflicts` (`GoalFinding`: code, message, and outcome, where
    `null` marks a note);
  - per measure `interventions` (relevance, outcome, benefit timing, preferred, and
    `site` / `cost` / `time` fits);
  - `catalogueVersion` and `baselineId`.

  There is no confidence or score.

- `Query.interventionCatalogue` returns the versioned catalogue (`interventions-3`, which
  adds wider effects and professional reviews per measure, ADR 0013).
  `costSources`, `evidence` and `effectModel` are empty until reviewed. `effectInputs`
  (`key`, `label`, `unit`, `minimum`, `maximum`, `required`, `note`) say what a measure's
  water effect depends on; the catalogue holds bounds only, never values (ADR 0012). A copy is in
  `docs/domain/interventions.catalogue.json` (`npm run intervention-catalogue`).

The agent tools in `application/tools/goals.py` (`check_goal`, `explain_goal_fit`,
`list_interventions`) call the same `GoalService` and return the same results.

## Scenarios and plan comparison

ADR 0012; rules in `docs/domain/option-engine.md`. Both engines are deterministic, exact
and versioned. A language model may turn words into a scenario, but never computes a
result.

- `ExactNumber { exact, value }`: `exact` is an integer or `p/q`, and `value` is a
  decimal string (28 significant digits). Clients round only for display. A missing value
  is `null`, never 0.
- `PlanningSession.scenarioComparison` gives the saved scenario against the same baseline:
  - `status`: `none`, `applied`, or `awaiting_confirmation` (parsed from words, not yet
    confirmed; results ignore it);
  - `rows` (`key`, `label`, `unit`, `baseline`, `scenario`, `change`, and `reason` when
    a value is unavailable), `notes`, `baselineId`, `engineVersion`.
- `Query.previewScenario(sessionId, scenario)` returns `ScenarioPreview { errors,
comparison }` without saving. Adjustments use `parameter` (`demand`, `piped_supply`,
  `rainfall`), `change` and a `quantity`: a `RATIO` in (0, 1] for relative changes, or
  the parameter's unit for `SET_TO`. Session saves and agent tools use the same
  validation (`scenario.adjustments.N.…` field errors).
- `PlanningSession.planComparison` returns `PlanComparison`:
  - `id`: the comparison key, a hash of the engine, catalogue, baseline, goal and scenario
    versions. Any change gives a new id;
  - `engineVersion`, `scenarioEngineVersion`, `catalogueVersion`, `baselineId`;
  - `status` (`OPTIONS`, `NO_FEASIBLE_PLAN`, `NEEDS_INPUT`, `TARGET_ALREADY_MET`,
    `NOT_SUPPORTED`) and `summary`;
  - `metric` (`TANKER_DEPENDENCE`, `SHORTAGE_DAYS`), `unit`, `baselineValue`,
    `scenarioValue`, `targetLevel`;
  - `options`: 0 to `maxOptions` (3) `ComparedOption`s, never padded;
  - `needs` (what would let more be compared), `excluded` (measures that cannot count, and
    why), `rejections` (counts of failed combinations), `assumptions`, `ranking` (the
    rule as text) and `stressTests`.
- `ComparedOption`:
  - `id` (derived from the comparison id and its measures), `rank`, `interventionIds`,
    `name`;
  - `measures` (`OptionMeasure`: water saved or added at low and high estimates, after
    the measures before it, so lines add up; cost, build days, benefit timing; and
    `effects`, every effect value the line was computed from, as `OptionEffect`: `key`,
    `label`, `unit`, exact `low` and `high`, and `origin` — `USER_ESTIMATE`, `BASELINE`
    (sourced baseline value) or `SCENARIO` (set by the confirmed what-if). The catalogue
    never supplies an effect value);
  - `pessimistic`, `optimistic`, `margin`, `waterLow`, `waterHigh`, `uncountedHigh`
    (water beyond the tanker deliveries it could replace, not counted);
  - `cost`, `buildDays`, `firstBenefit`, `why`, `tradeoffs`, `uncertainty`;
  - `sensitivity` (swing per estimate) and `stress` (`value` and `meetsTarget` per stress
    test, both `null` when the test does not apply).
  - `impact` (`WiderImpact`, below), assessed for every option before selection.
- `PlanComparison.impactContext` (`ImpactContext`) and `impactEngineVersion` (`impact-1`).
- `PlanOption` (stored when chosen) adds `comparisonId`, `engineVersion` and
  `interventionIds`, and `impact.wider` holds the `WiderImpact` exactly as shown.

### Wider-system impact

ADR 0013; rules in `docs/domain/impact-assessment.md`.

- `WiderImpact`:
  - `id`, `optionId`, `engineVersion`, `catalogueVersion`, `comparisonId`, and
    `inputHash` (SHA-256 over every input; any change gives a new id);
  - `localBenefits`, `externalities`, `falseResilience` and `tradeoffs`, each a list of
    `ImpactFinding`;
  - `reviews` (`ImpactReview`) and `context`.
- `ImpactFinding`:
  - `id`, `kind`, `statement`, `basis` (`ENGINE_ESTIMATE`, `MECHANISM`, `DECLARED`,
    `SOURCED`), `uncertainty`, `citations` (`ImpactCitation`: `kind`, `ref`, `label`,
    `asOf`), `interventionIds` and `related`;
  - beyond the site: `system` (`AQUIFER`, `CATCHMENT`, `SUPPLY_NETWORK`), `direction`
    (`POSSIBLE_BENEFIT`, `POSSIBLE_HARM`, `EITHER`) and `linkage` (`LINKED`,
    `NOT_LINKED`, `UNKNOWN`);
  - `magnitude` (`metricId`, `unit`, exact `baseline`, `atLowEstimates`,
    `atHighEstimates`) appears only on local benefits, and only for `tanker_dependence`
    or `shortage_days`. Effects beyond the site never carry a number.
- `ImpactReview`: `kind` (`STRUCTURAL`, `HYDROGEOLOGICAL`, `WATER_QUALITY`), `label`,
  `required`, `reasons` and `interventionIds`.
- `ImpactContext`:
  - `boundaries` (`InfluenceBoundary`: `level` `SITE`/`AREA`/`SHARED_SYSTEM`, `label`,
    `detail`, `system`, `linkage`, `citations`);
  - `nearby` (`NearbyPlace`: `name`, `communityId`, `distanceM`, and `links` per system
    with `linkage` and `evidenceIds`), within `nearbyRadiusM`. This is geography only:
    `UNKNOWN` unless one evidence record lists both areas;
  - `groundwater` (`SOURCED`, `DECLARED`, `NONE_RECORDED`, `UNKNOWN`) and
    `groundwaterCitations`;
  - `waterQuality` (`QualityReading`: `parameter`, exact `value`, `unit`, `observedOn`,
    `method`, `citations`) and `waterQualityNote`. There is no potability field;
  - `unavailable` (`UnavailableAssessment`: `key`, `label`, `reason`).
- `SiteConstraints.groundwaterUse` / `SiteConstraintsInput.groundwaterUse`: optional.
  Whether the site pumps from a borewell or well.
- `Report.planName` and `Report.impact`: the chosen option's name and impact assessment
  (with `wider`), copied when the report is finalized and never recomputed.
- Proposal inputs are `waterlens.proposal-inputs/2` (`inputs-v2.json`), with
  `report.planName` and `report.impact`. `ProposalSection` adds `WIDER_IMPACT`.

**Where scenarios are explored.** In the web app only Agent mode explores scenarios (the
agent pane's what-if tool, calling `previewScenario` and saving through the session).
Traditional mode has no what-if controls; the Plans page shows a saved scenario read-only,
labelled "Agent-generated" (ADR 0012 §6).

**Choosing a plan.** `updatePlanningSession` with `selectedPlanOptionId` recomputes the
comparison for the resulting inputs. The id must be among its current options, otherwise
`PRECONDITION_FAILED` with field `selectedPlanOptionId`. The option is stored before the
session transaction. Options stored before Prompt 11 (no `comparisonId`) keep the
revision rule above.

Agent tools in `application/tools/options.py` (`compare_plans`, `preview_scenario`,
`explain_option`, `check_impact_summary`) call the same `OptionService` and return the
same results, including each option's `impact`. `check_impact_summary(sessionId,
optionId, text)` returns `{ok, problems, impactId}`. A model-written summary is shown
only if:

- every sentence cites `[F:<finding id>]` or `[U:<unavailable key>]`;
- its numbers come from the cited findings;
- it neither certifies drinking water nor claims an absence of harm.

## Location

Covered by ADR 0009.

- **Queries:**
  - `resolveLocation(text)` returns up to five `PlaceCandidate`s, plus
    `needsClarification`, a plain-language `question` and the `provider`. It requires a
    principal (a guest is enough). Ambiguous names return several candidates and a
    question, and nothing is chosen for the person.
  - `reverseLocation(latitude, longitude)` returns named places near a point. It is
    empty when the provider is unavailable.
  - `countries` returns ISO 3166 alpha-2 codes with CLDR names.
  - `regionSettings(latitude, longitude, countryCode)` previews the currency, time zone
    and units inferred for a point, the options for each, and whether each is
    certain. It requires a principal and is shown in the review before confirming.
  - The web never puts `ResolveLocation` or `ReverseLocation` results in the query cache
    (provider caching terms). Only `Countries` is cached.
- **Mutation:** `confirmLocation(input)` creates or reuses an `Area` and is idempotent.
  - The `origin` must be `PLACE_SEARCH`, `GEOLOCATION` or `CUSTOM`.
  - `placeId` is required for `PLACE_SEARCH` only, and must carry the active provider's
    prefix.
  - `extent` is required, with no default: `REFERENCE_POINT`, or `USER_RADIUS` with
    `radiusMeters` from 100 to 50,000.
  - Optional `currency` (ISO 4217) and `timezone` (IANA) override the inferred values.
    Omitted or null keeps the inference.
  - The area id is derived from the confirmed content. Different details create a new
    area and never rewrite a shared one.
  - Coordinates are `DecimalString`s with at most 7 decimals. `countryCode` is required.
  - The mutation does not change the session. The client then sets `areaId` through
    `updatePlanningSession` (via the session coordinator).
- **New `Area` fields:**
  - `origin`, `scope`, `extent`, `radiusMeters`, `placeId`;
  - `private` (geolocation and custom areas, readable by the owner only; others get
    `NOT_FOUND`);
  - `formattedAddress`, `admin`, `accuracyMeters`, `currency`, `unitSystem`,
    `hasBoundary`;
  - `providerExpiresAt` and `providerContentExpired` (Google content older than 30 days
    must be chosen again);
  - `regionSetByUser`: which of `currency` and `timezone` the person chose instead of
    the inferred value.
- `Report.area` is nullable: it is null when the area is private to someone else.
- **`AreaReadiness.basis`:**
  - `SOURCED`: at least one capability is available.
  - `LIMITED`: only partial or stale coverage.
  - `USER_INPUT`: nothing covers the area, so the assessment uses only entered values
    and is labelled that way.

## Units, money and time

- **Rates** are `Quantity { value: DecimalString, unit: LITRES_PER_DAY }`. MLD is a
  display unit, produced only by formatting code (1 MLD = 1,000,000 L/day).
- **Money** is `Money { minorUnits: MinorUnits, currency, exponent }`.
  - INR has exponent 2, so `minorUnits` is paise. Existing `INR_paise` fixtures map
    1:1 and are never rescaled.
  - Other ISO 4217 codes are representable (USD, EUR, GBP with exponent 2; JPY 0; KWD 3)
    but there is no conversion. Costs exist only in currencies with a reviewed cost basis
    (INR today).
- **Instants** are `UtcDateTime` (`2026-10-10T06:00:00Z`). **Local dates** are
  `LocalDate` in the area's IANA timezone. Windows are half-open `[start, end)`.
- **Missing data** is `MeasuredValue { availability, quantity: null, reason }`. It is
  never zero.

## Pagination

Lists return `XConnection { nodes, pageInfo { hasNextPage endCursor } }`:

- `first` defaults to 20 and must be within 1..50;
- pass `after: endCursor` for the next page;
- order is newest first;
- cursors are opaque and only valid with the **same filter**; reusing one with another
  filter returns `VALIDATION_FAILED`.

Related records on a page (a community's area, the viewer's membership, a match's
scheme, a report's area) are loaded through per-request `DataLoader`s, so a page costs
one batched read per related type, not one read per row (ADR 0005 §7).

### Nearby communities

`nearbyCommunities(near: {latitude, longitude, radiusMeters}, first, after)` returns
active communities whose reference point (the centroid of their area) lies within
`radiusMeters` (100–50,000) of the point. Nodes are `{community, distanceMeters}`, sorted
by distance and then id. The server reads indexed geohash candidates (at most 50 per
cell), filters by exact great-circle distance and deduplicates. If any cell hit its cap,
`candidatesTruncated` is `true` and the client should suggest a smaller radius; results
are never padded or guessed. Communities without a reference point are not listed.
Invalid coordinates or radii return `VALIDATION_FAILED`.

## Invalidation

Implemented in `apps/web/src/graphql/invalidation.ts`. It runs after every answered
mutation, including typed errors, because a `VERSION_CONFLICT` needs the fresh record.

| Mutation                     | Invalidates (prefixes)                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `createPlanningSession`      | `['session','current']`, `['session']`                                                                                          |
| `updatePlanningSession`      | `['session', id]` (session, plan options, matches), `['session','current']`                                                     |
| `matchFunding`               | `['session', sessionId, 'derived']`                                                                                             |
| `finalizeReport`             | `['reports']`, `['session', sessionId]`                                                                                         |
| `archiveReport`              | `['reports']`, `['reports', id]`                                                                                                |
| `generateProposal`           | `['reports', reportId]`                                                                                                         |
| `createCommunity`            | `['communities']`                                                                                                               |
| `joinCommunity`              | `['communities', id]`, `['communities','list']`, `['communities','nearby']`, `['communities','mine']`                           |
| `leaveCommunity`             | the join set plus `['reports']` and `['projects']` (shared records may disappear)                                               |
| `archiveCommunity`           | `['communities']`, `['communities', id]`                                                                                        |
| `startImplementationProject` | `['projects']`                                                                                                                  |
| `updateMilestone`            | `['projects']`                                                                                                                  |
| `recordObservation`          | `['projects', projectId, 'observations']`                                                                                       |
| `recordManualInput`          | `['readiness']`, `['baseline']`, `['session', sessionId, 'derived']`; the coordinator then refreshes the session (new revision) |
| `confirmLocation`            | `['areas']` (the session's `areaId` is then set by the coordinator)                                                             |
| `beginAccountClaim`          | nothing (claims are not cached)                                                                                                 |
| `cancelAccountClaim`         | nothing                                                                                                                         |
| `completeAccountClaim`       | `['viewer']`, `['session']` (the guest's session now belongs to the account)                                                    |

`invalidateAfter` cancels in-flight fetches for each prefix before invalidating it.
TanStack Query otherwise joins a first load that is still running, and that load's
response, computed before the mutation, would be shown as current.

The session coordinator writes through `updatePlanningSession` itself and, after each
acknowledged write, invalidates `['session', id]` and `['session','current']`; when the
revision changed it removes `['session', id, 'derived']`.

Separately, the whole query cache is cleared whenever the signed-in uid or account kind
changes (sign-in, sign-out, linking). The clear runs synchronously in the auth state
handler, before the new identity renders, so no screen can show the previous
identity's data even for one frame.

Job progress is streamed, not polled through GraphQL. Clients load the job once with the
`job(id)` query, then open its `eventsPath` (SSE) through the shared Axios client (fetch
adapter, streamed body) with the bearer header, because `EventSource` cannot send
headers. Each `state` event carries `id`, `version`, `status` (lowercase), `stage`,
`attempts`, `maxAttempts`, `errorCode` and `updatedAt`; the client merges it into
`['jobs', jobId]` only when `version` is not older. The server closes a stream after
5 minutes or at a terminal state. Clients reconnect at once after a healthy stream, back
off (1 s to 30 s) otherwise, stop streaming after 5 consecutive failures, retry a 401 once
with a refreshed token, stop on 403/404, pause while hidden, and poll the query every 5 s
only while the stream is failing (`apps/web/src/features/jobs`, ADR 0007 §6). When the stream
reports a terminal state, they invalidate the owning record (for example
`['reports', reportId]`). `/jobs/:jobId` restores any job by id after a refresh.
